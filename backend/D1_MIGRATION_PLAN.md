# PostgreSQL to Cloudflare D1 migration plan

## Goal

Use Cloudflare D1, Cloudflare's managed SQLite service, for this backend so the Worker and its relational data store run on Cloudflare. Cloudflare Hyperdrive is a connection layer for an existing PostgreSQL/MySQL database; it does not provision a PostgreSQL database.

## Source-to-target mappings

| PostgreSQL implementation | D1 implementation |
| --- | --- |
| `pg.Pool` obtained from Hyperdrive | `D1Database` binding (`env.DB`) |
| `$1`, `$2` positional parameters and `pool.query()` | Prepared D1 statements with `?` placeholders and `.first()`, `.all()`, `.run()` |
| PostgreSQL `uuid` / `gen_random_uuid()` | UUID strings generated by `crypto.randomUUID()` at insert sites |
| PostgreSQL text arrays | JSON-encoded `TEXT`, decoded at repository boundary |
| PostgreSQL `boolean` | SQLite integer `0`/`1`, mapped to/from booleans |
| PostgreSQL `time` | `TEXT` in `HH:MM:SS` format |
| PostgreSQL timestamp and interval expressions | UTC ISO text for audit timestamps; Unix seconds for expiry and comparison |
| PostgreSQL migrations | D1 migrations in a separate `d1_migrations/` directory, preserving the original SQL files as a legacy reference |

## Architectural changes

- Bind one D1 database as `DB`; remove the Hyperdrive binding and PostgreSQL driver from Worker runtime code.
- Update the repository, AI-consent storage, OAuth transaction/code storage, and refresh-token storage to use parameterized D1 statements.
- Keep the public API contract, table/column names, identity keys `(auth_provider, auth_subject)`, and admin-controlled `role` invariant.
- Keep Google/OpenAI identity verification and Valora JWT signing behavior unchanged.
- Create the D1 database in the selected Rushikesh Cloudflare account, bind its returned ID, apply D1 migrations, then deploy the Worker.

## Invariants

- User data remains scoped to the resolved local UUID and cascades when the user is deleted.
- OAuth `state`, app codes, and refresh tokens remain one-use/rotating through atomic single-statement `DELETE ... RETURNING` and `UPDATE ... RETURNING` operations.
- All SQL values remain parameter-bound; only static SQL fragments are interpolated.
- D1 query results are converted to the same API record shapes as before.
- Existing PostgreSQL migrations remain untouched for reference/recovery; they are not applied to D1.

## Semantic differences and risks

- SQLite has no native arrays, booleans, UUID, time, or timestamp types; JSON text, integer booleans, UUID strings, time text, and UTC timestamps need explicit conversion.
- SQLite `RETURNING` is used only for single-row statements. D1 batch atomicity is reserved for independent multi-statement operations where required.
- Existing local PostgreSQL data is not automatically copied. Before switching a populated local database, export/import or retain the existing backend checkout/data. No production Worker or Hyperdrive database exists in the selected Cloudflare account at planning time.
- OpenAI and Google credentials still need configuration before live sign-in works; deployment itself must not depend on those optional provider secrets.

## Validation strategy

- Convert one representative repository operation first and inspect the query and mapping before converting the remaining persistence calls.
- Run TypeScript type checking after the D1 binding and code migration.
- Apply the migrations to the new D1 database and inspect the resulting migration status/schema.
- Review every SQL call for bound values, correct SQLite date handling, and one-time/rotation semantics.
- Deploy only after configuration references the created D1 database and production issuer URL.
